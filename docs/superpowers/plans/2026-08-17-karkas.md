# Каркас проекта — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Поднять проект Next.js с отрисовкой R3F и рабочими тестами, чтобы доказать жизнеспособность оснастки до появления сложности.

**Architecture:** Next.js App Router, холст R3F подключается через динамический ввоз с отключённым отрисовыванием на сервере. Все числовые константы — в `lib/config.ts` с первого коммита. Vitest гоняет чистые функции в окружении Node, без браузера.

**Tech Stack:** Next.js 16.3.1, React 19.2.8, TypeScript 5.9.3, three 0.185.1, @react-three/fiber 9.7.0, @react-three/drei 10.7.8, Tailwind CSS 4.3.3, zustand 5.0.15, Vitest 4.1.10.

Спека: `docs/superpowers/specs/2026-08-17-brick-sphere-design.md`, раздел 6.

## Global Constraints

- **Все числа — только в `lib/config.ts`.** Ни в компонентах, ни в тестах-снимках, ни в стилях числовых литералов быть не должно. Исключение — тесты: они задают значения у себя.
- **Каждое число в конфиге сопровождается комментарием**, объясняющим не «что это», а **почему именно столько** и **что сломается**, если поставить иначе.
- **Текст на русском** — комментарии, сообщения коммитов, описания PR, имена в конфиге. Без англицизмов там, где есть русское слово.
- **Пути и имена файлов — латиницей.** Кириллица в путях ломает сборку на хостинге: macOS хранит имена в нормализации NFD, Linux ожидает NFC, и путь ввоза перестаёт совпадать с именем файла. Локально работает, на деплое — нет. Внутри файлов имена и комментарии по-русски.
- **Версии пакетов, влияющих на картинку, закрепляются точно**, без диапазонов `^`: `next`, `react`, `react-dom`, `three`, `@react-three/*`, `tailwindcss`, `@tailwindcss/postcss`, `typescript`. Сцена чувствительна к версиям three и drei, а Tailwind v4 молод и менял поведение `@theme` между минорными версиями. Пакеты типов и линтер живут с диапазонами: на картинку они не влияют, а закреплять их — лишняя работа при каждом обновлении.
- **TypeScript берётся 5.9.3, не 7.x.** Седьмая версия — переписанный на Go компилятор; типы R3F и drei тяжёлые и обобщённые, и проверять их совместимость с новым компилятором в этом проекте не время. Поднять версию можно позже отдельной веткой.
- **Node на машине — 25.7.0, не LTS.** Next тестируется на 20 и 22. Сегодня не блокер; помнить при странных ошибках сборки.
- **База — `master`.** Рабочие ветки с префиксом `ft/`. Этап закрывается PR с описанием и скриншотами.

## Раскладка файлов

| Файл | Ответственность |
|---|---|
| `lib/config.ts` | Все числа проекта. Единственный файл, который правит человек при настройке. |
| `components/scene/SceneMount.tsx` | Клиентская обёртка. Динамический ввоз холста с `ssr: false`. Ничего больше. |
| `components/scene/SceneCanvas.tsx` | Сам `<Canvas>` и содержимое сцены. |
| `app/page.tsx` | Страница. Монтирует сцену на весь экран. |
| `vitest.config.mts` | Настройка тестов: окружение Node, псевдоним `@`. Расширение .mts, а не .ts: Vite грузит .ts-конфиг как CommonJS и ругается на ESM-синтаксис при каждом запуске тестов. |
| `tests/osnastka.test.ts` | Дымовой тест: доказывает, что three грузится в тестовом окружении. |

`SceneMount` и `SceneCanvas` разделены не ради красоты: `dynamic(..., { ssr: false })` запрещён в серверных компонентах Next, поэтому вызов обязан жить в отдельном клиентском файле.

## Задача 3: Vitest и дымовой тест

**Files:**
- Create: `vitest.config.mts`
- Create: `tests/osnastka.test.ts`
- Modify: `package.json` (раздел `scripts`)

**Interfaces:**
- Consumes: псевдоним `@/*` из задачи 2.
- Produces: команда `npm test`; псевдоним `@` работает и в тестах.

Тест намеренно проверяет загрузку `three`, а не арифметику. `three` поставляется как ESM-модуль, и именно это чаще всего ломается в тестовом окружении. Проверка `1 + 1` не доказала бы ничего.

- [ ] **Шаг 1: Поставить Vitest**

```bash
npm install --save-exact --save-dev vitest@4.1.10
```

- [ ] **Шаг 2: Написать падающий тест**

Файл `tests/osnastka.test.ts`:

```ts
import { describe, expect, it } from 'vitest'
import { Vector3 } from 'three'

describe('оснастка', () => {
  it('three загружается в тестовом окружении и считает длину вектора', () => {
    const вектор = new Vector3(3, 4, 0)
    expect(вектор.length()).toBe(5)
  })

  it('нормализация даёт единичную длину', () => {
    const вектор = new Vector3(3, 4, 0).normalize()
    expect(вектор.length()).toBeCloseTo(1, 12)
  })
})
```

- [ ] **Шаг 3: Запустить тест без настройки**

```bash
npx vitest run
```

Ожидается: `2 passed`. Красной фазы здесь нет и быть не может: Vitest находит `tests/**/*.test.ts` по умолчанию, а дымовой тест ввозит только `three` и `vitest`, без псевдонима. Запуск делается ради другого — убедиться, что `three` грузится в тестовом окружении **до** того, как появится настройка, которую можно будет обвинить в поломке.

Настройка из следующего шага нужна не для запуска, а для псевдонима `@` и окружения Node, которыми пользуются тесты раскладки в ветке `ft/sphere`.

- [ ] **Шаг 4: Написать настройку тестов**

Файл `vitest.config.mts`:

```ts
import { fileURLToPath } from 'node:url'
import { defineConfig } from 'vitest/config'

export default defineConfig({
  resolve: {
    // Тот же псевдоним, что в tsconfig.json. Без него тесты не смогут
    // ввозить модули так же, как это делают компоненты, и пути в тестах
    // разойдутся с путями в коде.
    alias: { '@': fileURLToPath(new URL('./', import.meta.url)) },
  },
  test: {
    // Окружение Node, а не браузера: тестируются только чистые функции.
    // Браузерное окружение здесь стоило бы секунд запуска и ничего не дало.
    environment: 'node',
    include: ['tests/**/*.test.ts'],
  },
})
```

- [ ] **Шаг 5: Запустить тесты**

```bash
npx vitest run
```

Ожидается: `2 passed`.

- [ ] **Шаг 6: Добавить команду в package.json**

В раздел `scripts` файла `package.json` добавить строку:

```json

```


- [ ] **Шаг 1: Написать конфиг**

Файл `lib/config.ts`:

```ts
/**
 * Единственное место в проекте, где живут числа.
 * Каждое значение объясняется: почему именно столько и что сломается иначе.
 */

export const сцена = {
  /** Цвет фона. Светлый намеренно: зритель в конце прокрутки выезжает
   *  из снежной сцены на светлый лендинг, и тёмный фон читался бы как
   *  переход на другой сайт. Здесь же он задаёт тон, под который
   *  подбирается цвет кирпича — кирпич должен быть темнее. */
  фон: '#e8ecef',

  камера: {
    /** Начальное положение камеры, метры. Отодвинута по всем трём осям,
     *  чтобы объект был виден в три четверти, а не в лоб: в лоб не
     *  читается ни объём, ни кладка. */
    позиция: [8, 5, 12] as [number, number, number],

    /** Поле зрения, градусы. Сорок пять — компромисс: шире даёт заметное
     *  искажение по краям кадра на широких экранах, у́же лишает сцену
     *  ощущения простора. */
    полеЗрения: 45,
  },

  /** ВРЕМЕННЫЙ раздел. Проверочный куб существует только чтобы доказать,
   *  что холст жив. Удаляется целиком в ветке ft/sphere вместе с кубом. */
  проверка: {
    /** Ребро куба, метры. */
    ребро: 2,
    /** Цвет куба. Темнее фона — заодно проверяем главное правило сцены:
     *  объект должен быть темнее снега, иначе он в нём растворяется. */
    цветКуба: '#6b7480',
    /** Яркость рассеянного света. Ниже — грани куба сливаются в чёрное. */
    рассеянный: 0.6,
    /** Положение направленного света, метры. Низко над горизонтом:
     *  скользящий свет цепляется за неровности и рельеф читается сам. */
    направленный: [5, 3, 5] as [number, number, number],
  },
}
```

- [ ] **Шаг 2: Написать холст**

Файл `components/scene/SceneCanvas.tsx`:

```tsx
'use client'

import { OrbitControls } from '@react-three/drei'
import { Canvas } from '@react-three/fiber'

import { сцена } from '@/lib/config'

export default function SceneCanvas() {
  return (
    <Canvas camera={{ position: сцена.камера.позиция, fov: сцена.камера.полеЗрения }}>
      <color attach="background" args={[сцена.фон]} />

      <directionalLight position={сцена.проверка.направленный} />
      <mesh>
        <boxGeometry args={[сцена.проверка.ребро, сцена.проверка.ребро, сцена.проверка.ребро]} />
        <meshStandardMaterial color={сцена.проверка.цветКуба} />
      </mesh>
      <OrbitControls />
    </Canvas>
  )
}
```

- [ ] **Шаг 3: Написать клиентскую обёртку**

Файл `components/scene/SceneMount.tsx`:

```tsx
'use client'

import dynamic from 'next/dynamic'

// Холст ввозится динамически с отключённым отрисовыванием на сервере.
// Одного 'use client' не хватает: клиентские компоненты всё равно проходят
// серверную отрисовку, а там нет window, и WebGL падает при монтировании.
// Сам вызов dynamic с ssr: false запрещён в серверных компонентах Next,
// поэтому он обязан жить здесь, в отдельном клиентском файле.
const SceneCanvas = dynamic(() => import('./SceneCanvas'), { ssr: false })

export default function SceneMount() {
  return <SceneCanvas />
}
```
